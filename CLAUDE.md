# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

FAIR Screenplay Utility — a tool run on local AI that turns video into a "screenplay": a combined transcript of speech and on-screen action, for use by researchers or other LLM classifiers.

**De-identification is a core design constraint, not an add-on.** This tool is meant to run on video containing PII, and its output must not let a reader re-identify anyone: no appearance (clothing, hair, build, age, ethnicity), no gender, no name (real or guessed, including a recognized show/public figure), no on-screen text/signage. What it must still capture faithfully: who said what (WhisperX diarization's `SPEAKER_NN` labels — reliable, and never touched by anonymization), gaze/orientation (who is looking at whom), and body language/gesture described as behavior. Every free-text-generating prompt in `src/prompts.py` folds in one of two anonymization-rules blocks for this reason — when adding or editing a prompt that produces natural-language description, compose one in rather than leaving unfiltered output. `ANONYMIZATION_RULES` (full) is for prompts called once per video (`write_screenplay`); `CAPTION_ANONYMIZATION_RULES` (condensed) is for `caption_video`'s per-frame prompts, since those calls are stateless with no cross-call caching and pay the full block's prompt-processing cost on every single sampled frame — the condensed version keeps the hard "never" constraints verbatim but trims the elaboration, trading some edge-case robustness for materially lower per-frame latency. Prompt compliance alone is probabilistic, so `src/screenplay/scrub_check.py` is a warn-only mechanical backstop (regex, not a model) that spot-checks generated captions/screenplay text for likely slips; it never blocks or modifies output, so its silence is not a guarantee — treat it as a spot-check aid, not a filter.

The pipeline orchestrates four models, all served locally:
- **WhisperX** (diarization scribe) — generates speech transcripts with speaker diarization. Runs via the `whisperx`/PyTorch stack directly (not Ollama), since Ollama has no ASR/diarization capability.
- **emotion2vec+** (tone classifier, `iic/emotion2vec_plus_large` by default) — classifies each diarized utterance's vocal tone (angry/happy/sad/etc.) straight from its audio span. Runs via `funasr`, not Ollama, since emotion2vec+ isn't servable there either.
- **Qwen3-VL** (visual action observer, `qwen3-vl:8b` by default) — generates captions describing what happens on screen, sampled at a fixed fps. Served locally by Ollama.
- **Ornith-1.5** (orchestrator/screenwriter, `ornith-1.5-255k` by default) — combines the tone-coded transcript and captions into the final screenplay Markdown, matching `screenplay_template.md`. Also served locally by Ollama. Ornith is not on the public Ollama registry, so it must already exist locally (`ollama list`) — it cannot be auto-pulled like Qwen3-VL.

**All four stages are implemented**, plus a `main.py` entry point that runs the full pipeline end-to-end. This is a change from earlier: the orchestrator stage used to be a placeholder and audio used to be extracted to a file on disk — both are now done differently (see Architecture below).

## Setup

```
pip install -r requirements.txt
```

For local development the user has created the 'screenplay' conda environment.

Both the captioning and orchestrator stages require a local [Ollama](https://ollama.com/download) install running in the background — those modules talk to Ollama's local HTTP API rather than loading model weights themselves, so no GPU/PyTorch setup is needed for those stages. This is a deliberate choice to keep the tool distributable to non-technical users without requiring a Python/CUDA environment; prefer Ollama-servable models over `transformers`-loaded ones for any new locally-run model in this project. WhisperX is the one stage that still needs the real PyTorch/whisperx stack, since diarization/ASR isn't available through Ollama. `src/tone/classify_tone.py` (see below) is a further deliberate exception to the Ollama-preference rule — do not "fix" it to go through Ollama; emotion2vec+ isn't servable there.

Config lives in `.env` (see `.env.example`): `HF_TOKEN` (required, for the pyannote diarization model), `WHISPERX_DEVICE`/`WHISPERX_COMPUTE_TYPE`/`WHISPERX_MODEL`/`WHISPERX_BATCH_SIZE`/`WHISPERX_LANGUAGE`, `CAPTION_FPS`/`CAPTION_MODEL`/`CAPTION_CONTEXT_CAPTIONS`/`CAPTION_MAX_DIMENSION`/`SPEECH_FRAME_OFFSET`/`SPEECH_BURST_FRAMES`/`SPEECH_BURST_SPACING`, `ORNITH_MODEL`, and `TONE_MODEL` (for the tone-classification stage).

## Architecture

- `src/video_utils/` — video preprocessing utilities, no `__main__` blocks (imported by other scripts, not run directly).
  - `extract_audio.load_audio_numpy_array(video_path)` decodes a video's audio track straight into an in-memory float32 mono 16kHz numpy array for WhisperX. It no longer writes an audio file to disk — there's no `extract_audio()`-to-file function or `data/audio/` output dir anymore.
  - `extract_frames.load_frames(video_path, fps=1.0, start_time=0.0, max_frames=None)` samples still frames from a video at a fixed wall-clock rate, returning `(timestamp, PIL.Image)` pairs.
  - `extract_frames.load_burst_frames_at(video_path, timestamps, burst_count=1, burst_spacing=0.2)` grabs, for each of a specific list of timestamps, up to `burst_count` frames at `t, t+spacing, t+2*spacing, ...` (rather than a fixed interval), in one combined decode pass — e.g. `caption_video.caption_video` below, to give the model a chance at noticing motion (mouth movement, a gesture) around a speech-start moment. The result is **positionally aligned** with `timestamps` (a miss is an empty inner list, not an omission) rather than a dict keyed by timestamp value — deliberately, so that a caller attaching identity (e.g. a speaker label) to each timestamp can zip results back safely instead of reverse-looking-up by a derived float, which risks silently colliding two different timestamps onto the same key.
  - Both use **PyAV** (`av`), not a shelled-out `ffmpeg` binary — PyAV ships precompiled ffmpeg libraries in its wheel, so no separate ffmpeg install is required. Keep this dependency-free-install property in mind when adding new video/audio processing: prefer libraries that bundle their own codecs over ones that shell out to external binaries.
- `src/captioning/`
  - `caption_video.caption_video(video_path, fps=1.0, start_time=0.0, max_frames=None, model_name=..., context_captions=1, utterances=None, speech_start_offset=0.5, burst_count=1, burst_spacing=0.2, max_dimension=1280)` — captions a video in a single chronologically-ordered pass. Fixed-interval frames come from `extract_frames.load_frames`; if `utterances` is given — a list of `{"start": float, "speaker": str}` dicts (deliberately just those two fields, e.g. projected from a tone-enriched transcript's records — not the full record, so dialogue `text` never reaches the vision prompt) — a burst of `burst_count` speech-triggered "reaction shot" frames per utterance, starting at `start + speech_start_offset` and spaced `burst_spacing` apart, is pulled in via `extract_frames.load_burst_frames_at` and merged in by timestamp with the fixed-interval ones; utterances whose first burst frame falls past the end of the video are skipped with a warning. Every frame/burst in the merged, timestamp-sorted sequence is then captioned in order, each with the previous `context_captions` captions fed back into the prompt (most recent last, regardless of which trigger produced them) so the model describes *what changed* rather than re-describing the whole scene each time. Pass `context_captions=None` to feed back every prior caption instead of a fixed window. Before being sent to Ollama, each frame is downscaled (long edge to `max_dimension` px, never upscaled — `None` sends native resolution) and JPEG-encoded instead of PNG, since Qwen3-VL's vision-token cost scales with pixel count and a source video's native resolution is well past the point of diminishing returns for reading gaze/body language; see `_resize_for_captioning`.

    A fixed-interval frame costs one Ollama call. A speech-start burst is captioned by chaining `burst_count` *sequential single-image* calls (`_caption_speech_burst` in `caption_video.py`) — the model is told which `SPEAKER_NN` just started talking and asked to weigh visual evidence (mouth movement, posture, gesture, gaze) across the burst to determine which visible person that is, falling back to neutral language if it can't tell — but only the final call's caption is promoted to the merged timeline, so bursting never inflates the event count downstream. This is deliberately sequential rather than one multi-image call: as of writing, sending several same-dimension frames in a single qwen-vl chat message can be silently fused into one frame by the tokenizer ([ollama/ollama#17321](https://github.com/ollama/ollama/issues/17321)) or return no response at all ([ollama/ollama#13047](https://github.com/ollama/ollama/issues/13047)) — both fail silently, unacceptable for a pipeline whose whole purpose is trustworthy de-identification. `burst_count=1` (the function default) skips the chain entirely, costing exactly one call like before bursting existed; `main.py` passes `SPEECH_BURST_FRAMES`/`SPEECH_BURST_SPACING` (default 2/0.2) as the real pipeline defaults.

    Returns records with `index`/`timestamp`/`timestamp_hms`/`caption`/`trigger` (`"fixed_interval"` or `"speech_start"`)/`mentioned_speakers` (any `SPEAKER_NN` tags regex-found in the caption text — a structured cross-check downstream consumers can use instead of re-parsing prose, since a tag can come from a grounded speech-start identification or one carried forward from context on either trigger type). Speech-triggered records also carry the originating `"speech_start"` timestamp and, when `burst_count > 1`, a `"burst_captions"` debug trail of the full per-frame chain (not surfaced to Ornith — `merge_screenplay` doesn't pass it through). `write_json` persists these to `data/captions/<name>.captions.json`. `main.py` builds `utterances` from the tone-enriched transcript directly — pass the same `{"start", "speaker"}` projection, not just the video, when replicating what `main.py` does.
- `src/transcription/` — WhisperX-based diarization pipeline (`diarize_transcript`) plus `format_transcript.format_segments`, which flattens raw WhisperX segments into per-utterance records (`start`/`end`/`start_hms`/`end_hms`/`speaker`/`text`/`word_count`/`avg_word_score`/`low_confidence_words`). `write_json` persists to `data/transcripts/`.
- `src/tone/`
  - `classify_tone.classify_tone(records, audio, model_name="iic/emotion2vec_plus_large", hub="hf", sample_rate=16000)` — adds an `"emotion"` (top label) and `"emotion_scores"` (per-label confidence dict) field to each formatted-transcript record, by slicing that utterance's span out of the full-video audio array and classifying it with emotion2vec+ (loaded via `funasr`, not Ollama — see Setup). Records with a zero-length span get `None`/`None` instead of erroring. `write_json` persists to `data/transcripts/<name>.formatted.tone.json`, deliberately distinct from `format_segments`'s own `.formatted.json` for the same video. This tone-enriched output, not the plain `.formatted.json`, is what feeds `merge_screenplay` below.
- `src/screenplay/` — the orchestrator stage.
  - `merge_screenplay.merge_screenplay(captions, transcript)` combines caption records (point-in-time "visual" events) and tone-enriched transcript records (start/end "speech" events, each carrying an `"emotion"` field) into one chronological list, sorted and re-indexed. Pass `classify_tone`'s output here, not the plain transcript — Ornith should never see an emotion-less transcript. Each "visual" event also carries a `"trigger"` field — `"fixed_interval"` or `"speech_start"` — normalized from the source caption record (defaulting to `"fixed_interval"` if absent), so consumers can tell `caption_video`'s fixed-fps captures apart from its speech-triggered reaction-shot ones, plus a `"mentioned_speakers"` field (any `SPEAKER_NN` tags `caption_video` found in the caption text) that Ornith's prompt uses to tell a grounded speaker attribution apart from one it would have to invent. `write_json` persists to `data/screenplays/<name>.screenplay.json`.
  - `write_screenplay.write_screenplay(events, template, model_name="ornith-1.5-255k")` sends the merged timeline JSON plus `screenplay_template.md` to the local Ornith model and returns the generated screenplay Markdown, following the template's scene/action/dialogue structure. The system prompt instructs Ornith to render a speech event's `"emotion"` as a parenthetical tone direction (e.g. `*(sad)*`) above the dialogue line, but only when it's a meaningful, specific tone — not `"neutral"`/`"other"`/unknown/null; it also carries the same de-identification rules as the caption prompts (Ornith's own prose synthesis is an independent leak surface, not just a relay of upstream captions) plus a rule against attributing a visual action to a `SPEAKER_NN` tag the source caption didn't already name, and a lightweight best-effort substitution for a name spoken in dialogue text. `write_md` persists to `data/screenplays/<name>.screenplay.md`.
  - `scrub_check.scrub_check(text, label)` — see the de-identification note under Project overview above. Called from `main.py` after captioning and after the final screenplay write; only logs warnings (gendered language / appearance words / likely proper names) and returns them, never modifies `text`.
- CLI entry points (each is the *only* place in its script that reads env vars or resolves default paths — everything else under `src/` stays a plain library that takes what it needs as arguments). `main.py` is the sole entry point kept at the repo root; every single-stage entry point lives under `src/cli/` and is run as a module (`python -m src.cli.<name> ...`) from the repo root, since they import via `from src...` and need the repo root on `sys.path`:
  - `main.py <video>` — runs the full pipeline: transcribe → classify tone → caption (fixed-fps + speech-start, scrub-checked) → merge → write screenplay (scrub-checked).
  - `src/cli/transcribe.py <video>` — audio extraction + diarized transcript only. Run as `python -m src.cli.transcribe <video>`.
  - `src/cli/caption_video.py <video>` — frame sampling + captioning only. Run as `python -m src.cli.caption_video <video>`.
  - `src/cli/build_screenplay.py <captions_json> <transcript_json>` — merge stage only (given existing captions/transcript JSON). Pass a tone-enriched transcript (`.formatted.tone.json`) here to match what `main.py` does, not the plain `.formatted.json`. Run as `python -m src.cli.build_screenplay ...`.
  - `src/cli/write_screenplay.py <screenplay_json>` — orchestrator stage only (given an existing merged screenplay JSON). Run as `python -m src.cli.write_screenplay <screenplay_json>`.
  - `src/cli/classify_tone.py <video> <transcript_json>` — tone-classification stage only (see `src/tone/` above), useful for re-running tone classification alone without redoing transcription. Re-decodes the video's audio to slice per-utterance clips, so it needs both the video and an existing formatted transcript JSON. Run as `python -m src.cli.classify_tone <video> <transcript_json>`.
- `screenplay_template.md` — the Markdown structure/formatting template Ornith is instructed to match exactly (scene headings with timestamp ranges, prose action lines, timestamped dialogue attributed by speaker).
- `data/raw_videos/` — source video files (input).
- `data/transcripts/`, `data/captions/`, `data/screenplays/` — per-stage JSON (and final `.md`) outputs. There is no longer a `data/audio/` stage since audio is decoded in-memory rather than written to disk.

## Data flow convention

Utility functions default their output paths to `data/<stage>/` relative to the repo root (each package computes `DEFAULT_OUTPUT_DIR` from `Path(__file__).resolve().parents[2]`). Follow this pattern for new pipeline stages so scripts can be run from anywhere in the repo without needing explicit output paths.
